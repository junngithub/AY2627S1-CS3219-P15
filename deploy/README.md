# deploy/

Everything that runs **inside** the clusters, as YAML in Git.

- **Cloud (nonprod, prod):** Argo CD applies it and keeps the cluster
  matching it. Terraform (`infra/`) builds the cluster and installs Argo CD
  plus a root Application pointing here.
- **Local:** `./local.sh` applies the **same charts and values** with Helm,
  straight from your working copy. There's no Argo CD and no push needed.

Design: [ADR-0008](../infra/docs/adr/0008-gitops-repo-layout.md),
[ADR-0009](../infra/docs/adr/0009-no-argocd-locally.md).

## Layout

```text
deploy/
  local.sh                         # local cluster: helm install/upgrade everything (up | status | down)
  push-local.sh                    # local cluster: build + push an image to Floci ECR, restart what runs it
  charts/                          # LEVEL 1: plain Helm charts (work without Argo CD)
    foc-namespace/                 #   ResourceQuota, LimitRange, NetworkPolicy for one env
    strimzi/                       #   wrapper: vendored strimzi-kafka-operator 1.2.0 (charts/*.tgz)
    foc-kafka/                     #   Kafka 4.3.1 + node pool + 7 topics + 5 users with ACLs
    foc-service/                   #   generic chart for any of the 7 services
    envoy-gateway/                 #   wrapper: vendored Envoy Gateway 1.9.2 + GatewayClass (one per cluster)
    foc-gateway/                   #   one env's entry point: Gateway, routes, auth, header stripping
  values/
    clusters/<cluster>/strimzi.yaml  # per cluster: which namespaces Strimzi watches
    services/<svc>.yaml              # per service, same in every env: port, Kafka user, env vars
    envs/<env>/
      common.yaml                    #   applied to every service in the env: image registry, pull policy
      namespace.yaml                 #   resource quota for the env
      kafka.yaml                     #   brokers, replication, storage, memory
      services/<svc>.yaml            #   only what differs per env: image.tag, replicas
  argocd/                          # LEVEL 2: Argo CD objects (no Helm templating)
    projects/foc-platform.yaml     #   AppProject for Strimzi (may create cluster-wide objects)
    projects/foc.yaml              #   AppProject for everything else (FoC namespaces only)
    nonprod.yaml  prod.yaml        #   per cloud cluster: Strimzi Application + 3 ApplicationSets
# LEVEL 3: root Application, created by Terraform (infra/modules/argocd)
```

| Cluster | Environments → namespace | Applied by |
|---|---|---|
| local (Floci k3s) | local → `foc` | `./local.sh` (Helm) |
| nonprod (EKS) | dev → `foc-dev`, stg → `foc-stg` | Argo CD: `argocd/nonprod.yaml` |
| prod (EKS) | prod → `foc` | Argo CD: `argocd/prod.yaml` |

## What Argo CD creates per cloud cluster

| Argo object | Generates | Chart | Values (later files win) |
|---|---|---|---|
| `strimzi` Application | the Strimzi operator in `strimzi` | `charts/strimzi` | `clusters/<cluster>/strimzi.yaml` |
| `foc-namespaces` ApplicationSet | `<env>-namespace` per env | `charts/foc-namespace` | `envs/<env>/namespace.yaml` |
| `foc-kafka` ApplicationSet | `<env>-kafka` per env | `charts/foc-kafka` | `envs/<env>/kafka.yaml` |
| `foc-services` ApplicationSet | `<env>-<svc>` for **each file** in `envs/<env>/services/` | `charts/foc-service` | `services/<svc>.yaml` → `envs/<env>/common.yaml` → `envs/<env>/services/<svc>.yaml` |

**Ordering.** Kafka objects need Strimzi's CRDs, and services need the
Secrets Strimzi creates for Kafka users. Argo CD doesn't order Applications
generated by ApplicationSets, so every app **retries** until its dependencies
exist (`retry`, `SkipDryRunOnMissingResource`). A service pod waits in
`CreateContainerConfigError` until its Kafka Secret appears, then starts.

## How requests get in (gateway, ADR-0007)

```text
client ─▶ Envoy (envoy-<namespace> Service, type LoadBalancer)
           │  1. strip client-sent x-user-id / x-is-admin
           │  2. public exact path?  → forward to the service, no auth
           │     /api/v1/user/authorize → 404 at the gateway
           │  3. protected prefix?    → ask user:3000/api/v1/user/authorize
           │        401 → back to the client
           │        200 → add x-user-id / x-is-admin from the answer, forward
           ▼
         the service (ClusterIP)
```

| Prefix | Service |
|---|---|
| `/api/v1/user` | user |
| `/api/v1/supplier` | supplier (`GET /api/v1/supplier` exactly is public) |
| `/api/v1/credit` | credit |
| `/api/v1/orders` | order |
| `/api/v1/rating` | rating |
| `/api/v1/badges` | badges |
| `/api/v1/admin` | admin |

Locally: `deploy/local.sh gateway`, then
`curl -H 'Authorization: Bearer stub:alice@u.nus.edu' localhost:8080/api/v1/orders`.

## How services reach each other and Kafka

Identical in every environment, because each env's Kafka and services share
a namespace:

| Target | Address |
|---|---|
| another service | `http://<name>:<port>`, e.g. `http://credit:3000` |
| Kafka | `KAFKA_BROKERS=kafka-kafka-bootstrap:9093` (TLS + SCRAM-SHA-512) |

### Peer URLs (env vars)

Callers get their peers' addresses as environment variables, set in
`values/services/<svc>.yaml` under `env:`. Read them in code instead of
hard-coding hosts or ports:

| Service | Gets |
|---|---|
| order | `CREDIT_SERVICE_URL`, `SUPPLIER_SERVICE_URL`, `RATING_SERVICE_URL`, `ADMIN_SERVICE_URL`, `USER_SERVICE_URL` |
| admin | `USER_SERVICE_URL` |
| credit | `USER_SERVICE_URL` |
| badges | `USER_SERVICE_URL`, `ORDER_SERVICE_URL` |
| user, supplier, rating | none (rating only uses Kafka) |

Values look like `http://credit:3000`, the same in every environment. Calls
between services go **directly**, not through the gateway, so the caller
passes along the identity it received (`x-user-id` / `x-is-admin`, or the
bearer token). Each service's `helm test` also calls `/health` on every
`*_SERVICE_URL` it has, so a wrong name or port fails `deploy/local.sh check`.
If a service's port changes, update its `port:` and every URL pointing at it
(`grep -r <svc>: deploy/values`), plus the route in `charts/foc-gateway/values.yaml`.

`enableServiceLinks` is off, so pods don't also get Kubernetes' legacy
`<SERVICE>_PORT_*` variables (e.g. `KAFKA_KAFKA_BOOTSTRAP_*`), which would
clash with the `KAFKA_*` settings.

A service with `kafka.user` set also gets `KAFKA_USERNAME`, `KAFKA_PASSWORD`
(from the Secret Strimzi creates), `KAFKA_SASL_MECHANISM=SCRAM-SHA-512`, and
`KAFKA_CA_CERT=/etc/kafka/ca/ca.crt` (Kafka's TLS certificate authority).

## Common changes

| To… | Change | Then |
|---|---|---|
| release a new build to dev | `image.tag` in `values/envs/dev/services/<svc>.yaml` (CI does this) | Argo rolls the Deployment |
| promote to stg / prod | PR copying that `image.tag` into `envs/stg` / `envs/prod` | same, after review |
| add a service to an env | `values/services/<svc>.yaml` once + `values/envs/<env>/services/<svc>.yaml` | ApplicationSet creates `<env>-<svc>` |
| add a topic | `topics` in `charts/foc-kafka/values.yaml` | Strimzi creates it |
| let a service read/write a topic | its entry under `users` in `charts/foc-kafka/values.yaml` | Strimzi updates the ACLs |
| resize Kafka | `values/envs/<env>/kafka.yaml` | Strimzi rolls the brokers |
| roll back | `git revert` | Argo restores the previous state |

The chart refuses bad values at render time: a replication factor above the
broker count, a user referencing an undeclared topic, or a service with no
image registry, name or tag.

## Local development

Prerequisites: Floci running and `infra/local/aws` applied
([`infra/docs/local-floci.md`](../infra/docs/local-floci.md)), plus `helm`
and `kubectl`.

```bash
deploy/local.sh           # install / upgrade everything from your working copy
deploy/local.sh status    # releases, Kafka objects, pods
deploy/local.sh check     # helm test: Kafka logins + every ACL, HTTP to every service, requests through the gateway
deploy/local.sh gateway   # port-forward the gateway to http://localhost:8080 (prints example curls)
deploy/push-local.sh credit   # rebuild credit-service, push to local ECR, restart deploy/credit
deploy/local.sh down      # uninstall everything, delete namespaces foc + strimzi (and Kafka data)
```

`up` runs in dependency order and waits where it matters:
1. namespace `foc` (quota, limits, network policy);
2. Strimzi CRDs (server-side apply, so upgrades update them too), then the
   operator in `strimzi`;
3. Kafka, waiting until the cluster, topics and users are Ready (so the user
   Secrets exist);
4. one Helm release per `values/envs/local/services/<svc>.yaml`, using the
   same three layered values files as Argo CD in the cloud.

A service whose values file you deleted is uninstalled on the next run, like
Argo CD's prune. It's safe to rerun at any time. To check output without a
cluster:

```bash
cd deploy
helm template credit charts/foc-service \
  -f values/services/credit.yaml -f values/envs/local/common.yaml \
  -f values/envs/local/services/credit.yaml
```

The Argo CD files (`argocd/`) are **not** used locally. They first run in dev.

## Connectivity tests (`helm test`)

Both charts include Helm tests, which `deploy/local.sh check` runs. Argo CD
ignores them.

| Chart | Test pod | Checks |
|---|---|---|
| `foc-kafka` | `kafka-test-acls` (Kafka CLI, same image as the brokers) | built from the `users` table: every allowed write and read works (consumer group `<user>-conntest`); per user, one forbidden write and one wrong-prefix group are denied; a wrong password is rejected |
| `foc-service` | `<svc>-test-http` (curl) | `GET http://<svc>:<port><healthPath>` from another pod, plus `/health` on each `*_SERVICE_URL` in its `env`, retrying for ~20 s |
| `foc-gateway` | `foc-gateway-test` (curl) | 22 requests through Envoy: every route reaches its service; 401 without or with a bad token; admin flag; spoofed `x-user-id` / `x-is-admin` replaced or stripped; public routes work without a token; `/api/v1/user/authorize` and unknown paths give 404 |

Test pods are kept until the next run, so `kubectl -n foc logs kafka-test-acls`
still shows the last result.

## Updating Strimzi

1. Change `version` in `charts/strimzi/Chart.yaml`.
2. `helm dependency update charts/strimzi`, which re-vendors the `.tgz` and
   updates `Chart.lock`.
3. Check the release notes for supported Kafka versions and update
   `kafka.version` / `kafka.metadataVersion` in `charts/foc-kafka/values.yaml`.
