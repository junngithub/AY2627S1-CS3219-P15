# ADR-0008: GitOps layout for `deploy/`: same repo, three levels, ApplicationSets

- **Status:** Accepted
- **Date:** 2026-10-01
- **Refines:** ADR-0005 (paths and Argo object types)
- **Amended by:** [ADR-0009](0009-no-argocd-locally.md). The local cluster uses
  Helm via `deploy/local.sh`; `argocd/local.yaml` no longer exists.

## Context

`deploy/` holds everything Argo CD applies to the clusters. The first sketch
had hand-written `Application` files per env, a Strimzi chart pulled straight
from its public repo, and a full values file per service per env. Checked
against:

- Argo CD [Best Practices](https://argo-cd.readthedocs.io/en/stable/user-guide/best_practices/):
  keep config in a separate repo; manifests must not change meaning without a
  Git change.
- Argo CD [Cluster Bootstrapping](https://argo-cd.readthedocs.io/en/stable/operator-manual/cluster-bootstrapping/):
  prefer ApplicationSets; app-of-apps is an admin-only alternative.
- Codefresh, [How to structure your Argo CD repositories](https://codefresh.io/blog/how-to-structure-your-argo-cd-repositories-using-application-sets/):
  - no environment branches;
  - template once (Helm in the charts only);
  - no Helm values inside `Application`s;
  - avoid external charts;
  - use ApplicationSets;
  - use a three-level structure.

## Decision

**Same repository as the source code, with guard rails.** A separate config
repo is Argo's recommendation, but one repo is simpler for this project. The
risks are covered by:

- CI ignores changes under `deploy/**` (path filters);
- tag-bump commits made by CI carry `[skip ci]`, so CI can't trigger itself;
- a `CODEOWNERS` rule on `deploy/values/envs/prod/**` requires review before
  anything reaches prod.

**Three levels:**

```text
deploy/
  charts/                   # 1. plain Helm charts; installable without Argo
    foc-service/            #    generic chart for the 7 services
    foc-kafka/              #    Kafka, KafkaNodePool, KafkaTopic ×7, KafkaUser ×5
    foc-namespace/          #    ResourceQuota, LimitRange, NetworkPolicy (Argo creates the namespace)
    strimzi/                #    wrapper chart: pinned strimzi-kafka-operator, vendored .tgz
  values/
    clusters/<cluster>/     #    per cluster: strimzi.yaml (watched namespaces)
    services/<svc>.yaml     #    same in every env: port, Kafka user, env vars
    envs/<env>/common.yaml  #    every service in the env: image registry, pull policy
    envs/<env>/services/<svc>.yaml  # only what differs: image.tag, replicas
    envs/<env>/kafka.yaml   #    brokers, replication, storage
    envs/<env>/namespace.yaml #  resource quota
  argocd/                   # 2. Argo objects, no Helm templating
    projects/foc-platform.yaml # AppProject for Strimzi (cluster-wide objects allowed)
    projects/foc.yaml       #    AppProject: FoC apps may only deploy to FoC namespaces
    local.yaml              #    Strimzi Application + ApplicationSets for the local cluster (env: local)
    nonprod.yaml            #    ApplicationSets for nonprod (envs: dev, stg)
    prod.yaml               #    ApplicationSets for prod (env: prod)
# 3. root Application, created by Terraform (modules/argocd) → deploy/argocd/<cluster>.yaml
```

- Environments are **folders**, never branches.
- Helm templating happens **only** in `charts/`. ApplicationSets generate
  `Application`s using a Git generator over `values/envs/<env>/services/`, so
  adding a service means adding its values files, with no Argo YAML changes.
- Each service `Application` uses layered values:
  `values/services/<svc>.yaml`, then `values/envs/<env>/common.yaml`, then
  `values/envs/<env>/services/<svc>.yaml`.
- Third-party charts are pinned through wrapper charts in Git, never
  referenced live from their public repos.
- **Ordering by retries, not sync waves.** Argo CD doesn't apply sync waves
  across Applications generated by ApplicationSets. So each app retries until
  its dependencies exist: Kafka uses `SkipDryRunOnMissingResource` until
  Strimzi's CRDs appear, and service pods wait for their Kafka Secrets.
  (Corrected on 2026-10-01; the first version of this ADR said sync waves.)

## Consequences

- A release is a one-line change to `image.tag` in `values/envs/dev/services/<svc>.yaml`.
  Promotion is a PR copying it to `stg`, then `prod`.
- One repo means one PR can change code and deploy config together. Reviewers
  must watch for that.
- Moving `deploy/` to its own repo later only changes the `repoURL` in the
  ApplicationSets and the root Application.
