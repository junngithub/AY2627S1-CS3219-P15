11. ADMIN USER MANAGEMENT - ADD THREE ROWS (22 OCTOBER 2026)
------------------------------------------------------------
All three require Authorization: Bearer <real-admin-session-token>. Admin must
forward this header on its outbound calls. UUID-only / x-is-admin headers are
not administrator credentials. Invalid/non-admin callers
get 404; each mutation rechecks current actor/session state inside its transaction.

Method: GET
Endpoint: /api/v1/user/search
Body / Params: ?q=&page= ; admin bearer header
Purpose: Search account name/email case-insensitively or exact UUID. q max 100
characters, page 1-100000 (default 1), page size 20. Returns 200
{ items: [{ id, name, email, role, status }], page, total }. role is admin/user;
status is Created/Verified/Suspended. Stable ordering, expired deletion records
excluded, Cache-Control: no-store. Passwords/tokens/private Telegram IDs omitted.
Malformed query: 400 INVALID_QUERY or INVALID_PAGE.

Method: POST
Endpoint: /api/v1/user/{userId}/role
Body / Params: { role: "admin" | "user" } ; UUID path parameter; admin bearer header
Purpose: Persist promotion/demotion. Returns 200 { userId, role, status, changed }.
Only active unlocked fully verified targets can be promoted. Self-demotion is
rejected; last available admin cannot be demoted. Actual changes atomically
update the role, increment authVersion, revoke sessions/reset links and record
User audit. Unchanged retries return changed:false. The target logs in again.

Method: POST
Endpoint: /api/v1/user/{userId}/status
Body / Params: { status: "suspended" | "verified" } ; UUID path parameter; admin bearer header
Purpose: Persist suspension/reinstatement. Returns 200
{ userId, role, status, changed }. The body value "verified" means remove
suspension, NOT mark verification complete. An unfinished user returns Created;
timestamps and password lockout are preserved. Actual changes revoke sessions
and reset links; suspension additionally revokes OTP/Telegram challenges. No
extra credit event/grant is produced. Last available admin cannot be suspended.

Mutation errors: 400 INVALID_USER_ID / INVALID_ROLE / INVALID_STATUS /
SELF_DEMOTION_FORBIDDEN; 404 USER_NOT_FOUND or hidden caller denial;
409 LAST_ADMIN / USER_NOT_ELIGIBLE / USER_PENDING_DELETION.

These use the requested admin-authorized paths, not new unauthenticated internal
APIs. User stores its transactional audit; Admin still owns its own audit/events
after 200. This is not a distributed transaction. Admin relay forwarding is
implemented; frontend items/id/role mapping still needs updating. No shared
contract file, Admin/frontend source or deployed mesh setting is edited here.
See the README's Admin integration instructions and deployment acceptance checklist.

12. UPDATE LOGIN'S PURPOSE (F2.3)
------------------------------------------------------------
Keep POST /api/v1/user/login and { email, password } unchanged. Use:

F2/F2.2/F2.3. Public. Success returns
{ token, tokenType, expiresAt, user: { id, name, email, status } }.
Locks the account after five failed password attempts by default and attempts
one warning email on the transition into lockout. Counters are serialized under
a user-row lock; concurrent/repeated attempts cannot each trigger a warning for
the same lockout. Correct login before the threshold resets failed attempts.
The warning directs the owner to the frontend forgot-password page. Successful
password reset unlocks the account and revokes existing sessions. Suspended,
already-locked and deletion-expired accounts do not trigger repeated warnings.
Unknown accounts, wrong passwords, active locked accounts and deletion-expired accounts
return 401 INVALID_CREDENTIALS with the same generic message, including when
sending fails. With the correct password and before the deletion deadline, a
suspended account returns 403 ACCOUNT_SUSPENDED even when lockedAt is set:
suspension is checked before lockout. No session is issued and no lock cleared.
Appeals still reject locked accounts with generic 401; password reset must clear
the lock before an appeal can proceed. This is the approved exception to the backlog's
generic-login-error rule, enabling the separate public suspension appeal route.
Existing suspension/reinstatement operations remain unchanged.

Delivery note: uses the existing SES/development/disabled provider, not the
Kafka outbox. A failed warning is not queued for retry; the account stays locked. A crash
after saving lockout may lose the warning. SDK retries may cause duplicate
delivery after an ambiguous network response. There is no exactly-once delivery
guarantee or backfill for accounts locked before deployment. Existing SES and
FRONTEND_BASE_URL settings apply; no new endpoint/body, migration, dependency or
AWS permission is introduced. Automated checks use fake SES; actual lockout
email receipt remains a deployment acceptance check. The shared contract itself
has not been edited by this guide.

13. FRIENDSHIPS - UPDATE FIVE ROWS AND ADD REQUEST LIST (27 OCTOBER 2026)
------------------------------------------------------------
Apply these changes manually to the User Service table in the shared Google
Docs contract. This guide is not evidence that the external document was edited.
Update the existing send/accept/reject/list/remove rows, and ADD the new
GET /api/v1/user/friends/requests row so recipients can discover request IDs.

All six endpoints require Authorization: Bearer <real-user-session-token>.
The actual session and current account state are checked; x-user-id or other
identity headers alone are not credentials. Callers must be active, with neither
deletion requested nor scheduled. Following the contract's auth-only rule,
completed email/Telegram verification and permittedAction=true are not additional
requirements. There is no Order participation lookup. All responses use
Cache-Control: no-store. Friendship user summaries contain only id/name; no
passwords, email, Telegram details or role are returned.

Method: POST
Endpoint: /api/v1/user/friends/request
Body / Params: { targetUserId }; target account UUID; bearer header
Purpose: Send an invitation. Returns 201
{ requestId, senderId, recipientId, status: "pending", createdAt }.
Rejects self-requests. The target must exist, be active and have no pending
deletion. At most one pending or accepted row may exist per unordered pair,
including crossed/concurrent sends; conflicts return 409, never auto-accept.

Method: GET
Endpoint: /api/v1/user/friends/requests
Body / Params: ?direction=incoming|outgoing&page=1&pageSize=20 ; bearer header
Purpose: NEW ROW. Discover pending incoming (default) or outgoing invitations.
Returns 200 { items: [{ requestId, status: "pending", createdAt,
sender: { id, name }, recipient: { id, name } }], page, pageSize, total }.
Only pending rows with an available peer are returned; rejected/removed history
is not exposed by this list.

Method: POST
Endpoint: /api/v1/user/friends/{requestId}/accept
Body / Params: requestId UUID in path; no body; bearer header
Purpose: Recipient only. Returns 200
{ requestId, status: "accepted", changed }. Pending becomes accepted with
changed:true; repeating acceptance while still accepted returns changed:false.
The sender must remain available, including on a retry. A sender or unrelated
caller receives 404; incompatible state receives 409.

Method: POST
Endpoint: /api/v1/user/friends/{requestId}/reject
Body / Params: requestId UUID in path; no body; bearer header
Purpose: Recipient only. Returns 200
{ requestId, status: "rejected", changed }. Pending becomes rejected with
changed:true; repeating rejection while still rejected returns changed:false.
An available recipient may reject even when the sender is suspended or pending
deletion. A sender or unrelated caller receives 404; incompatible state is 409.

Method: GET
Endpoint: /api/v1/user/friends
Body / Params: ?page=1&pageSize=20 ; bearer header
Purpose: List accepted friends in either direction. Returns 200
{ items: [{ id, name }], page, pageSize, total }. Suspended peers and peers with
deletion requested/scheduled are excluded, as they are from the request list.

Method: DELETE
Endpoint: /api/v1/user/friends/{friendUserId}
Body / Params: other user's UUID in path (NOT requestId); no body; bearer header
Purpose: Changes an accepted relationship to REMOVED. Returns 204 with no body;
idempotent even if no accepted relationship exists. Does not cancel a pending
invitation. An available caller may remove an unavailable peer.

Both lists: page defaults to 1 (integer 1-100000); pageSize defaults to 20
(integer 1-100). Stable order is createdAt descending, then request UUID
ascending. total counts matching visible rows before pagination.

Errors: 400 INVALID_USER_ID for missing/malformed UUIDs (including requestId),
SELF_FRIEND_REQUEST for sending to self, INVALID_PAGINATION or INVALID_DIRECTION
for malformed list queries; 401 UNAUTHORIZED for unusable session/account;
404 USER_NOT_FOUND for missing/unavailable send target or
FRIEND_REQUEST_NOT_FOUND for missing request/wrong actor;
409 FRIENDSHIP_ALREADY_EXISTS for an active unordered relation,
FRIEND_REQUEST_NOT_PENDING for incompatible accept/reject state, or
USER_NOT_AVAILABLE when the acceptance sender is unavailable.

Storage: Friendship.id is requestId; status is PENDING/ACCEPTED/REJECTED/REMOVED
in PostgreSQL and lowercase on the wire. Rejected/removed rows remain history;
resending creates a fresh UUID, so an old request cannot accept a new invitation.
Both User foreign keys cascade on physical account deletion. Migration
20261027000000_friendships adds a not-self CHECK and a custom partial unique
index on the unordered pair while PENDING/ACCEPTED. These SQL constraints are
not fully represented by Prisma 5's schema; use the migration workflow rather
than relying on db push. This guide claims no normal-database migration or
deployment. Reported validation on 27 October 2026: Prisma Client generation,
prisma validate, TypeScript build, 74/74 unit tests and
node --check scripts/friendships.integration.cjs passed.
test:integration:friendships passed
against real local PostgreSQL in a disposable user_friendships_it_<random>
database, which was dropped afterward. It covered all six HTTP endpoints,
auth denials/spoofing, input bounds, discovery/privacy, bidirectionality and
idempotency, fresh IDs on re-invitation, concurrent crossed sends/accept-reject,
direct database self/pair constraints, transactional revoked-session checks,
pagination and cascades. All five existing isolated regression suites also
passed after the new migration/code: email, lifecycle, admin-bootstrap,

14. USER REPORTS AND SUSPENSION APPEALS (30 OCTOBER 2026)
------------------------------------------------------------
Add these User Service rows; the shared Google Docs contract itself has not been
edited. Generic /api/v1/user/me/escalate is not implemented. Created-account
verification help still needs an agreed API; this feature handles user reports
and suspension appeals only.

Method: POST
Endpoint: /api/v1/user/reports
Body / Params: { reportedUserId, comment }; real user bearer header
Purpose: Derives reporterUserId from the actual session, never body IDs or
spoofed identity headers. Reporter must be active with neither deletion requested
nor scheduled; session/account are rechecked transactionally. reportedUserId must be
a UUID (400 INVALID_USER_ID), must not be self (400 SELF_REPORT), and must exist
before its deletion deadline (404 USER_NOT_FOUND otherwise). Suspended targets
and accounts awaiting a future deletion deadline remain reportable. comment is
trimmed to 1-4000 characters (400 INVALID_SUPPORT_TEXT). Invalid/unusable reporter
session/account: 401 UNAUTHORIZED. Submission does not suspend anyone.
Forwards only { reporterUserId, reportedUserId, comment } to private Admin
POST /api/v1/admin/reports. Returns 201 with a validated, identity-matched,
allowlisted Admin record, preserving its snake_case fields:
{ id, reporter_user_id, reported_user_id, comment, status, created_at,
closed_at, closed_by_admin_id }.
status: open | dismissed | actioned. closed_at/closed_by_admin_id may be null.

Method: POST
Endpoint: /api/v1/user/appeals
Body / Params: { email, password, message }; PUBLIC, no bearer session needed
Purpose: Normalizes email and trims/verifies the password as login does.
message is trimmed to 1-4000 characters (400 INVALID_SUPPORT_TEXT). With valid
input, unknown account, wrong password, locked account or passed deletion
deadline returns generic 401 INVALID_CREDENTIALS. Correct credentials for an
active account return 409 ACCOUNT_NOT_SUSPENDED. The account/password state is
rechecked under an account lock before forwarding. A suspended account with
valid credentials forwards only { userId, message } to private Admin
POST /api/v1/admin/appeals; no password or bearer token is forwarded by either
intake call. No session is created, no deletion cancelled, and no reinstatement
performed. Returns 201 with the validated, identity-matched, allowlisted record:
{ id, user_id, message, status, created_at, closed_at, closed_by_admin_id }.
status: open | rejected | reinstated. closed_at/closed_by_admin_id may be null.

Both routes set Cache-Control: no-store. Admin owns persistence and review.
Admin keeps one OPEN appeal per user and one OPEN report per ordered
reporter/target pair; a retry returns the original record and original text.
This is not a lifetime submission limit; closure allows a later submission.
User holds no account locks during the HTTP call. There are no new User tables
or migrations for reports/appeals; the friendship migration still needs normal
deployment. Existing suspend/reinstate operations are unchanged.

Public appeal throttling: best-effort process-local AppealAttemptLimiter uses
normalized email hashes, including unknown emails, with 10 attempts per
15 minutes and at most 10,000 entries. Attempt/capacity exhaustion returns
429 TOO_MANY_APPEAL_ATTEMPTS. Expired entries are reclaimed; it resets on restart
and is not distributed across replicas. Ingress rate limiting is still needed.

ADMIN_SERVICE_BASE_URL defaults to empty: eligible submissions return
503 ADMIN_NOT_CONFIGURED, while other account APIs remain usable. A configured
value must be an HTTP(S) origin without credentials, non-root path, query or
fragment. .env.example uses http://localhost:8084 and User local Compose defaults
to http://host.docker.internal:8084. No real .env was edited. The request timeout
ADMIN_REQUEST_TIMEOUT_MS defaults to 5000 and is capped at 30000 ms. The client
rejects redirects, bounds responses to 32 KiB and performs no automatic retry.
Network/timeout errors or Admin 429/5xx: 503 ADMIN_UNAVAILABLE.
Invalid/oversized/malformed response: 502 ADMIN_INVALID_RESPONSE.
Other rejected upstream status: 502 ADMIN_REQUEST_REJECTED.
Upstream 409: 409 ADMIN_CONFLICT.
Errors are sanitized, without logging raw upstream errors or payloads. A failed
response can follow persistence; a manual retry uses open-record deduplication.
