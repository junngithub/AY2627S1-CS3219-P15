# Database schema

Flyway owns the schema. Hibernate validates it and does not create or alter tables. Migrations `V1` through `V5` in `src/main/resources/db/migration` produce the tables below. There are no foreign keys: `order_id` columns are plain UUIDs.

`orders.status` is the live record. `order_log` is an append-only history of successful transitions. It is not replayed and it is not a Kafka event.

## orders

One row per errand.

| Column | Type | Notes |
| --- | --- | --- |
| id | UUID | Primary key, generated by the service |
| requester_id | VARCHAR(320) | Gateway user id, required |
| requester_telegram_handle | VARCHAR(64) | Optional header value |
| courier_id | VARCHAR(320) | Set on accept, cleared when the order returns to CREATED |
| courier_telegram_handle | VARCHAR(64) | Same lifecycle as `courier_id` |
| requester_rating | DOUBLE PRECISION | Snapshot at create from Rating Service (`GET /api/v1/rating/{userId}`). Null when the user has no ratings yet |
| courier_rating | DOUBLE PRECISION | Snapshot at accept from Rating Service. Null when the courier has no ratings yet |
| item_description | VARCHAR(500) | Required |
| amount | INTEGER | Reward in credits. Check constraint `amount >= 1` |
| status | VARCHAR(32) | `OrderStatus` name |
| request_time | TIMESTAMPTZ | Create time |
| acceptance_expiry | TIMESTAMPTZ | Caller-supplied. After this, a still-open order expires |
| delivery_deadline | TIMESTAMPTZ | Caller-supplied. Must be after acceptance expiry |
| collection_deadline | TIMESTAMPTZ | Accept time plus 5 minutes. Cleared when the courier is cleared |
| acknowledgement_deadline | TIMESTAMPTZ | Set at collect: delivery deadline plus 1 day |
| settled_at | TIMESTAMPTZ | Set when the order becomes ACKNOWLEDGED or UNACKNOWLEDGED |
| pickup_location_id | VARCHAR(64) | Supplier id, stored as text |
| pickup_name | VARCHAR(200) | Name returned by Supplier Service |
| pickup_lat, pickup_lng | DOUBLE PRECISION | Used for proximity ranking |
| dropoff_location_id | VARCHAR(64) | Order `delivery_point.id` as text |
| dropoff_name | VARCHAR(200) | Snapshot |
| dropoff_building | VARCHAR(200) | Snapshot |
| dropoff_description | VARCHAR(500) | Snapshot |
| dropoff_lat, dropoff_lng | DOUBLE PRECISION | Snapshot |
| collection_photo_ref | VARCHAR(500) | Storage key, not a public URL |
| delivery_photo_ref | VARCHAR(500) | Storage key |
| dispute_photo_ref | VARCHAR(500) | Optional escalation photo |
| dispute_text | VARCHAR(2000) | Requester comment on a manual escalation |
| case_id | VARCHAR(64) | Copied from an admin Kafka event |
| fault_party | VARCHAR(16) | Set on admin resolve: `requester` \| `courier` \| `no-fault`. Exposed on REST as `faultParty` |
| created_at, updated_at | TIMESTAMPTZ | `updated_at` changes on every successful transition |

Indexes:

- `orders_status_idx` on `status`
- `orders_pickup_lat_lng_idx` on `(pickup_lat, pickup_lng)`
- `orders_requester_id_request_time_idx` on `(requester_id, request_time DESC)`

`V4` renamed `requester_email` and `courier_email` to `requester_id` and `courier_id`. The column type stayed `VARCHAR`.

`V6` adds `delivery_point`, `user_delivery_point`, and order dropoff `building` / `description` snapshot columns. `V7` adds optional `user_delivery_point.nickname`. `V8` adds `orders.fault_party`. `UserDeleted` on `foc.user.status` deletes that user’s associations and soft-inactivates orphan forks (see [delivery-points.md](delivery-points.md)).

## order_log

One row per successful status change, written in the same transaction as the order update. Rejected actions write nothing. System deadline actions store a null `actor_id`.

| Column | Type | Notes |
| --- | --- | --- |
| id | UUID | Primary key |
| order_id | UUID | Order that changed |
| action | VARCHAR(64) | `OrderAction` name |
| from_status | VARCHAR(32) | Null on create |
| to_status | VARCHAR(32) | Status after the change |
| actor_id | VARCHAR(64) | Caller user id, or null for the sweeper and admin consumer |
| occurred_at | TIMESTAMPTZ | |

Index: `order_log_order_occurred_idx` on `(order_id, occurred_at)`.

Postgres triggers `order_log_no_update` and `order_log_no_delete` reject `UPDATE` and `DELETE` with `order_log is append-only`.

Actions: `CREATED`, `ACCEPTED`, `CANCELLED`, `RELEASED`, `COLLECTED`, `DELIVERED`, `ACKNOWLEDGED`, `ESCALATED`, `COLLECTION_WINDOW_EXPIRED`, `ACCEPTANCE_EXPIRED`, `DELIVERY_DEADLINE_MISSED`, `ACKNOWLEDGEMENT_WINDOW_EXPIRED`, `COMPLETION_WINDOW_ELAPSED`, `REVIEW_STARTED`, `CASE_RESOLVED`.

## alerts

A notification row written with every status change. `GET /alerts` returns rows where the caller is the requester and `notify_requester` is true, **or** the caller is the courier and `notify_courier` is true. Couriers are notified for the dispute lifecycle only: `ESCALATED`, `UNDER_REVIEW`, and case-resolved `COMPLETED` (when `faultParty` is set). The 7-day completion writes `notify_requester = false` and does not notify the courier.

| Column | Type | Notes |
| --- | --- | --- |
| id | UUID | Primary key |
| order_id | UUID | |
| requester_id | VARCHAR(320) | |
| courier_id | VARCHAR(320) | Null until a courier has accepted |
| from_status | VARCHAR(32) | Null on create |
| to_status | VARCHAR(32) | |
| notify_requester | BOOLEAN | |
| notify_courier | BOOLEAN | |
| created_at | TIMESTAMPTZ | |

Indexes: `alerts_requester_id_created_idx` on `(requester_id, created_at DESC)`; `alerts_courier_id_created_idx` on `(courier_id, created_at DESC)` where `notify_courier`.

## outbox

Delivery buffer for Kafka. A failed publish does not roll back the order. See [interfaces.md](interfaces.md).

| Column | Type | Notes |
| --- | --- | --- |
| id | UUID | Primary key |
| order_id | UUID | Also the Kafka message key |
| topic | VARCHAR(120) | |
| message_key | VARCHAR(64) | Order id |
| payload | TEXT | JSON event |
| created_at | TIMESTAMPTZ | |
| published_at | TIMESTAMPTZ | Null until the broker accepts the record |

Index: `outbox_unpublished_idx` on `created_at` where `published_at IS NULL`.

## processed_events

Idempotency for consumed admin events. The row is inserted before the order is updated. A repeated `eventId` is ignored. An unknown order id is still recorded, so a later retry of that same event does nothing.

| Column | Type | Notes |
| --- | --- | --- |
| event_id | VARCHAR(64) | Primary key |
| processed_at | TIMESTAMPTZ | |
